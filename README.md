# cloud-web

一个基于 GitHub 仓库作为存储后端的网页版网盘。**全站一体部署在腾讯云 EdgeOne（EO）边缘函数上**：`eo.js` 单文件同时提供前端页面、静态资源、认证用户 API、GitHub 代理与下载中转，浏览器的一切请求（含下载中转）都与站点同源，GitHub key 只保存在 EO 服务端，永不出现在用户端。

> 该项目代码由 AI 辅助编写。

## 功能总览

- **文件浏览**：文件夹层级导航、面包屑、文件/文件夹大小显示（文件夹大小由 git tree 递归统计）；标题右侧显示全仓**总用量**（数据量，与刷新倒计时之间有分隔线间隔）
- **自动刷新**：每 45 秒自动刷新文件列表，标题右侧显示刷新倒计时；标签页隐藏时暂停轮询，恢复可见时立即刷新
- **增量渲染**：列表按 key 做 diff，仅更新变化的文件大小文本（带高亮闪烁）、增删对应条目（带过渡动画），不再整列表闪屏；后台刷新失败保留原列表仅 toast 提示
- **懒加载**：文件过多的目录首屏按每批 40 条分批渲染（带"正在加载 x / y"尾部提示与入场动画），逐批进入视野即显示，大目录不再长时间白屏；后台刷新仍走增量 diff
- **请求优化**：
  - 数据请求与站点同源（EO 边缘函数），无第三方 API 依赖；**背景图由浏览器直连图床**（loliapi 302 到真实图片），不经 EO 中转，减轻边缘函数流量
  - GitHub API 使用 ETag 条件请求（304 不占速率限制、不触发重渲染），经 EO 原样透传
  - 变更操作（上传/编辑/删除）后开启 15 秒缓存穿透窗口，请求附加时间戳绕过代理与 ETag 缓存
  - 页面不缓存、JS/CSS 按构建时间戳长缓存；首屏无需预取配置/凭据，直接加载
- **上传**：
  - 支持多文件、文件夹拖拽/选择上传
  - 大文件自动分片（45MB / 30MB 两档，按 base64 后不超过 GitHub 单文件限制反算切片大小），`too large` 时自动降档续传
  - **Git 数据 API 管线（根治提交冲突）**：与 git 对象模型一致——文件内容先以 blob 对象上传（`POST /git/blobs` 不移动引用，任意并行**零冲突**），全部传完后每 40 个 blob 合成一个 tree + commit 批量落盘（引用移动次数从 N 次降到每 40 个 1 次）；**多组之间链式推进**——上一组提交成功的新引用直接作为下一组基点，跳过重新读引用，杜绝组间读到过期引用导致的非快进（non-fast-forward）失败；仅当引用被其他写入者抢先移动（422/409）时才从最新引用（带时间戳参数防缓存）重建 tree 重试，最多 8 次，与 git rebase 同理不丢他人提交；未提交的 blob 是悬空对象（列表不可见、GitHub 自动回收），**停止/失败天然无副作用，无需回退清理**
  - 并行上传：并行数可选（自适应 / 1 / 2 / 3(默认) / 5 / 自定义 1-10），上传中修改立即生效
  - **上传双通道**：开始上传前自动探测 CF 代理的写能力（必失败请求体探测，不产生提交；失败 60 秒后自动重探），探测结果 toast 明示；CF 侧持有服务端 key 时启用（`cf-worker.js` 配置 `GITHUB_TOKEN` 环境变量即在服务端注入鉴权，key 只在服务端，浏览器不接触），任务按两通道**在途均衡 + 实测速率比例加权分配**（带 15% 概率地板，零速率通道也能持续获得探测任务，快的通道分得更多，分片详情面板显示 EO×n / CF×m 任务数）；探测不可用自动仅走 EO
  - 自适应算法（激进策略）：初始并发 3、上限 8；分片 <15s 完成即升档、>45s 才降档；失败降档
  - **停止上传**：上传中可随时停止——中止全部在途传输；blob 未提交不产生任何仓库变更，仓库保持原样
  - **后台挂起**：上传中关闭弹窗自动转入后台，右下角浮泡实时显示进度、点击恢复；任务快照定期写入 localStorage，整页刷新后浮泡仍以"已中断"样式提示（传输本身无法在刷新后继续，属浏览器限制）
  - 可展开**速度曲线图**（Win10 资源管理器风格：总/EO/CF 三曲线每秒分通道采样、平滑路径（中点二次贝塞尔）+ 半透明面积填充 + 网格参考线 + Y 轴峰值/半值刻度，图例实时显示三路速度，标题栏显示峰值）
  - 单分片失败自动重试 3 次（递增退避）；409 及 `is at <sha> but expected <sha>` 引用冲突独立重试 6 次（退避 + 随机抖动）
  - 实时总速率与进度条；预计剩余时间（ETA）：综合实测总速率、小文件请求延迟（按大小文件占比加权）、剩余任务数与提交冲突率估算
  - 可折叠"分片详情"面板显示每个进行中分片的进度与速率
  - 上传前检测当前目录同名项（文件夹提示合并、文件提示覆盖），确认后继续
  - 失败自动清理残留分片
- **下载**：
  - **双通道加速**：大文件（>2MB）分 12 段滚动调度并行下载，段在 EO（同源，服务端注入 key 稳定无限流）与 CF 代理（cloud-ecr.pages.dev）两条链路间按**在途均衡 + 实测速率比例加权分配**（某通道在途任务多 2 个以上先补给在途最少通道；速率加权带概率地板（双通道 15% / 三通道 10%），零速率通道也能持续分到探测任务，杜绝"分不到段→测不到速率→永远分不到段"的通道饿死；无速率数据时在可用通道间轮询兜底，单段小文件批量下载同样各通道均衡；图例显示各通道在途段/片数 ×n），聚合带宽；段失败自动换源**续传**（从已收位置继续 Range，不重复拉取），CF 连续失败 2 次即熔断、剩余段全部回退 EO，保证最终可用性；大小未知时从响应 Content-Length 补出，不额外发探测请求
  - **外部多代理（可选）**：进度条卡片"多代理"开关开启后，从同源 `/api/proxies` 拉取公共 ghproxy 镜像列表（EO 逐个探测连通性，**只返回当前可用的**，实例级缓存 5 分钟；约 30 个候选内置），段/片在 EO / CF / 外部代理三通道间同样按在途均衡 + 速率加权分配，进一步聚合带宽；外部代理按代理熔断（单个代理连续失败 2 次轮换下一个，全部熔断自动退出外部通道）；开关状态持久化，下载速度曲线同步增加**外部（紫）**通道曲线与图例；外部代理仅用于匿名下载，写操作永不经过
  - **下载并发控制**：进度条卡片上可选择并行数（自适应 / 1 / 2 / 3 / 4 / 6 / 8 / 自定义 1-16），旁边实时显示当前实际并行数（×N），更改后立即生效（调度器即时补位）；自适应算法针对下载特性修改（无提交冲突）：连续 3 个段/片快速完成（<3s）自动升档（最高 8），EO 段/片失败自动降档（最低 1），CF 失败只熔断通道不降并发
  - **下载速度曲线**：进度条卡片可展开曲线图（总=蓝/EO=绿/CF=橙/外部=紫，按通道分桶每秒采样，平滑路径，外部曲线仅在多代理开启时绘制），Y 轴带峰值/半值刻度，图例实时显示各路当前速度与在途段/片数
  - 单文件下载先合并为 Blob 再用 ObjectURL 保存（跨域时 `download` 属性会被忽略，直接跳转预览的问题由此规避），底部**进度条卡片**实时显示百分比、已下载大小与速率，可点 ✕ 中止
  - 分片文件并发合并下载，每片同样在 EO/CF/外部代理间加权分配、失败换源重试与熔断回退，同样驱动进度条卡片
  - 复选批量下载：串行逐个下载（完成/失败一个再下一个，避免浏览器拦截并发自动下载并互相抢占带宽），进度条按字节汇总总进度，首个文件提示浏览器多文件拦截的处理方式，可随时停止并立即中止当前传输
  - **文件夹打包下载**：右键文件夹即可下载，经 git tree 收集全部文件（分片文件按组归并还原）后逐个拉取，在前端打包为 **zip**（store 模式不压缩，媒体文件无压缩收益且速度快；UTF-8 文件名、保留子目录结构）一次性保存，全程总进度条，可取消
  - 写操作默认走 EO（key 由 EO 在服务端注入）；上传可经 CF 中转加速——仅当 CF 侧持有服务端 key 时启用（`cf-worker.js` 配置 `GITHUB_TOKEN` 环境变量，运行时自动探测），GitHub key 永不下发浏览器；引用类操作（提交/删除）始终固定走 EO；提交冲突由 409/sha 竞争重试算法保证安全（见下文"关键算法"）
- **批量操作**：文件卡片点击切换选中（✓ 高亮），文件夹点击进入不参与选择；底部操作栏提供全选 / 反选 / 批量下载 / 批量删除 / 取消，有选中时才显示
- **删除**：单线程顺序删除，避免并行提交引用冲突；引用移动冲突按文件独立重试 8 次（退避 + 抖动）；已不存在的文件（404）幂等跳过；失败报告已删进度；文件夹/批量删除在弹窗内显示**删除进度条**（n / total · 百分比）与**停止按钮**（在途文件删完后停止调度，已删保留、其余不动）
- **预览**：
  - 视频 / 音频：流式加载，URL 直接交给媒体元素按 Range 边下边播，无需等待整文件下载；打开时探测拉取文件头部 1MB 测得真实下载速度，实时显示速度与已缓冲百分比，完成后保留 3 秒；开始播放或加载出错即停止测速探测，避免与播放器争抢带宽（分片视频仍需完整拉取；分片音频每收完一段分片即可播放已下载部分，用户与控件交互后不再换源，合并完成后自动切换完整文件并恢复进度、音量与倍速）
  - 音频播放器定宽占满容器（原生控制条不被压缩、音量按钮常驻），**默认音量 20%**，音量/静音状态跨预览记忆
  - 图片：fetch 分块流式读取，部分数据渐进渲染边下边显示，角落与加载文案实时显示下载速度与百分比；大图（>512KB 且服务器支持 206）自动切 4 段 Range 并行拉取（多线程加速），渐进渲染只取已连续完成的前缀分段，并行度不影响边下边显示；基线 JPEG 等非渐进格式收完前无法解码属正常，加载文案持续显示进度；关闭预览即中断下载，不浪费带宽
  - 图片查看器：工具栏 放大/缩小/适应/1:1，滚轮缩放、双击切换适应与实际大小、放大后拖拽平移；当前目录多图时显示**缩略图条**与前后切换按钮（← → 方向键同样可切换），切换走浏览器缓存即时呈现；缩略图**延后加载**（主图首次解码后才加载，带宽优先给当前图片）；放大后右下角显示**鸟瞰图**（整张图缩小 + 当前视口矩形，固定在不滚动的包装层上，拖动图片时不会跟着跑），拖动矩形快速定位；查看区纯白底 + 平滑重采样，照片颜色/细节更自然
  - 文本：纯文本或代码着色（按扩展名自动识别 JavaScript / JSON / Python / C 等，可手动切换），长行不换行走水平滚动；右侧显示**鸟瞰图**（行密度缩略条 + 视口框，点击/拖动快速定位；代码按行首 token 类型着色，与代码高亮同色板；行数超过可视高度时按像素行聚合并降低透明度，高行数不糊成片；静态内容离屏绘制一次，滚动只重绘视口框）
  - Markdown：默认渲染预览（标题/列表/引用/代码块/GFM 表格/链接/图片等），可切回纯文本查看原文
- **在线编辑**：文本编辑支持着色（透明 textarea 叠加高亮层）与 Markdown 编辑预览切换，保存经鉴权后通过 contents API 提交
- **属性面板**：文件 SHA、大小、分片数；文件夹包含文件数、子文件夹数、总大小；音频文件异步读取 ID3v1/ID3v2 标签（Range 请求只取文件头尾，不下载整文件；分片文件取首/尾分片），显示**歌手/标题/专辑/年份**
- **服务状态**：左下角角标实时显示 EO 边缘函数的连通性、RTT（HEAD 轻量测量）、出口 IP/归属地/ISP（不显示站点网址），每 10 分钟自动检测；检测完成 4 秒后角标**淡出**为半透明（悬停恢复），减少常驻视觉干扰；点击角标立即重新检测，检测中再次点击会中止当前轮并重新开始（页面/API/代理同体，单点检测即可反映全站状态）
- **路径兼容**：路径段仅解码一次保证字面名可访问；显示层反复解码，历史遗留的编码乱码名称显示为可读中文，重名时追加 `[原名: ...]` 标记区分
- **安全细节**：外链均带 `noopener`；所有文件名渲染走 `textContent`/转义，无 XSS 注入点；Markdown 渲染的链接/图片 URL 经协议白名单（拒绝 `javascript:`/`data:`/`vbscript:`）与引号过滤，杜绝属性逃逸注入；管理后台错误提示一律 `textContent` 渲染，服务端返回文本不进入 HTML
- **登录策略**：会话始终持久化（默认"保持登录"，无 UI 开关）；"记住密码"默认勾选（可取消），**只存 SHA-512 哈希不存明文**——自动填充时密码框显示占位符，未修改则直接用缓存哈希登录，修改即按新密码处理；旧版明文记录首次读取时自动哈希迁移
- **外观细节**：保持原有浅色卡片风格，细节优化——弹窗/右键菜单/操作栏入场动画、输入框聚焦高亮、按钮悬停阴影与按压反馈、细滚动条、toast 淡入

### 运行原理

1. **存储**：文件存放在另一个 GitHub 仓库（构建时由环境变量 `CLOUD` 指定，格式 `owner/repo`）。目录列表走 contents API，文件夹统计走 git trees API——全部经 EO 代理路径 `/api.github.com/...` 访问，key 由 EO 在服务端注入。
2. **单页应用**：EO 对所有未命中子路径返回同一主页面（SPA 兜底），`app.js` 根据 `location.pathname` 解析当前目录并加载列表。
3. **大文件分片**：超过分片大小的文件切成 `名称.part1、.part2 ...` 上传；列表展示时按后缀归并为一个虚拟文件，下载/预览时并发拉取分片合并为 Blob。上传走 Git 数据 API：内容先以 blob 对象并行上传（不动引用、零冲突），传完后每 40 个 blob 合成一个 tree + commit 批量落盘（详见下文"关键算法"）。
4. **鉴权**：所有密码类参数（登录、改密、注销、管理员鉴权 `admin_pass`、添加/重置用户密码）均在浏览器本地用 `crypto.subtle` 计算 SHA-512 哈希后再经 HTTPS 传输，**明文密码不出浏览器**；服务端只接受 128 位十六进制哈希（传明文返回 400），且所有响应不返回密码哈希（用户列表中的密码字段脱敏为 `***`）。登录只调 `/api/login` 校验并保存 `{用户名, 哈希, 角色}` 于 localStorage（会话始终持久化，即默认"保持登录"）；**前端不再接触任何 GitHub key**——上传/编辑/删除等写操作在请求头携带 `X-Auth-User` / `X-Auth-Pass`（即缓存的密码哈希），EO 逐请求实时校验后代为写 GitHub。"记住密码"默认勾选（可取消），只保存密码的 SHA-512 哈希用于下次自动填充（密码框显示占位符，未修改即哈希直登，修改则按新密码哈希；旧版明文记录自动迁移）。管理员（role=admin）显示"用户管理"入口，用户列表走 `/api/users`（管理员凭据即缓存哈希，无需重复输入密码，服务端脱敏返回），按 admin 靠前排序，支持搜索与折叠；添加用户（前端哈希后传输）、重置密码、调整角色、删除用户走鉴权 API，每次操作成功后自动刷新列表。所有用户可通过"我的账户"自助修改密码（新密码要求 >8 位且含大小写字母与数字，客户端先行校验）与注销账户（密码确认后永久删除并清除本地凭据）。
5. **代理与下载中转**：`ghUrl()` 把一切 GitHub URL 改写为同源路径（`/api.github.com/...`、`/raw.githubusercontent.com/...`、`/github.com/<owner>/<repo>/archive/...`），EO 仅放行白名单存储仓库，读操作公开、写操作鉴权；状态码、ETag、Content-Range 原样透传（304 条件请求、206 分段流式预览可用），请求/响应体流式转发不落地；用户数据仓库被白名单永久拒绝，任何后端数据（key、密码哈希）都不会出现在用户端。
6. **安全模型**：页面带 CSP/`nosniff`/`X-Frame-Options` 等安全头；背景图由浏览器直连图床（CSP `img-src` 放行 https），服务端 `/api/bg` 中转接口保留备用且仅放行 `image/*`；用户文件鉴权读有 60 秒实例级缓存（分片上传高频鉴权不重复回源），写后立即刷新。

### 关键算法

#### 自适应上传并行数

并行数 `limit` 在上传过程中动态调整（选择"自适应"时初始为 3，范围 1-8）：

```
分片完成耗时 dur = 完成时间 - 该次尝试开始时间
若 dur < 15s 且 limit < 8  → limit + 1   （网络宽裕，提速，激进升档）
若 dur > 45s 且 limit > 1  → limit - 1   （明确拥堵才降压）
分片普通失败重试前         → limit - 1   （失败暗示链路饱和）
每发生 2 次提交冲突(409/sha竞争) → limit - 1 （并行提交压力过大）
连续 8 个任务无提交冲突    → limit + 1   （低冲突率奖励，竞争压力小）
```

调度器 `fillUploads()` 始终维持在途任务数 = 当前 `limit`，因此手动改并行数或自适应调整都会立即生效；分片大小降级续传时保留已学到的 `limit`。

**下载并发自适应（无冲突版）**：下载段/片在途数不超过当前限制（自适应初值 3，范围 1-8）；连续 3 个段/片完成耗时 <3s → limit + 1（带宽宽裕）；EO 段/片失败 → limit - 1（链路饱和）；CF 失败只熔断 CF 通道不降并发（换源续传即可）。

#### 预计剩余时间（ETA）

```
实测总速率 speed   = 已传字节数 / 已耗时
传输剩余时间       = 剩余字节数 / speed
小文件延迟项       = 剩余任务数 × 小文件平均请求耗时 × 小文件占比 / 当前并行数
                    （小文件 = 分片 < 1MB，其耗时主要是请求往返而非传输）
冲突惩罚项         = (冲突次数 / 已完成任务数) × 剩余任务数 × 3s
ETA = 传输剩余时间 + 小文件延迟项 + 冲突惩罚项
```

每秒随速率采样刷新，显示为 `45% · 3.2MB/s · 预计剩余 2分30秒`。

#### 上传零冲突管线（Git 数据 API）

contents API 每次写都立即移动 git 引用，并行写必然竞争 409。上传改为 git 对象模型：

```
传输阶段：文件/分片 → POST /git/blobs（纯对象创建，不动引用，任意并行零冲突）
提交阶段：每 40 个 blob → （首组读最新 ref，后续组直接以本批上一组的新引用为基点）
         → 读 base tree → POST /git/trees（base_tree 合并）
         → POST /git/commits → PATCH /git/refs（全批唯一的引用移动点）
组间链式推进：不再重复读 ref，杜绝"上一组刚移动引用、下一组读到旧引用"的非快进失败
引用被抢先移动（422/409）→ 从最新 ref（带时间戳参数防中间缓存）重建 tree 重试，
最多 8 次（退避 1s×次数 + 随机抖动，不丢他人并发提交）
```

停止/失败时未提交的 blob 为悬空对象（不被任何 tree 引用、列表不可见、GitHub 定期回收），无需回退清理。删除仍为单线程顺序执行（contents API），单个文件遇冲突独立重试最多 8 次（`1.2s × 次数 + 抖动`），404 幂等跳过。
